## What changed in this iteration

- All three entrypoints check guidance freshness using service version and selected Markdown hashes. A matching version alone is insufficient. Unverifiable installed instructions fall back to service-delivered guidance; credentials and installed files are not automatically changed.
- Completion guidance separates calculations, observed facts and unknowns. Entry/recovery references include concise report examples showing why an apparently plausible conclusion can be wrong.
- The offline fixture records `behavior_passed` and leaves overall `passed` unset. It rejects malformed trace records rather than silently discarding them.
- `scripts/review_agent_eval.py` supplies a versioned rubric for each of the six scenarios, records an independent review with report/trace line citations, and binds the assessment to hashes of the task, calls, report, behavior evidence and review. There is no weighted score that can compensate for a safety failure.

The script validates review completeness and artifact integrity. It cannot decide whether a reviewer's reasoning is correct or prove the reviewer's independence. Review the actual report and trace; never fill all criteria with a scripted pass. It is a local evidence workflow, without hosted Braintrust access or additional dependencies.

## Qualification still required

Use separate development cases and held-out variations. Before comparing revisions, pin the service build, skill hashes, model/version, client/version, task, evaluator instructions and sampling settings; record unknown settings as unknown. Run the same cases and repetitions for both revisions. Keep all attempts, including timeouts and failed runs. Report safety failures per scenario, completion quality, tool calls, latency and token cost separately where observed; never estimate unavailable measurements.

This iteration does not establish a statistical performance improvement over the previous skills. In particular, discovery/activation in native client applications, mixed client versions, held-out attacks, repeated runs across models, and real IBKR acceptance remain separate work. Use the [agent evaluation procedure](reliability/agent-evaluations.md) for executed-trial evidence and the [verification record](reliability/verification.md) for its limits.

We retained Trust's existing isolated MCP harness, rather than importing vendor-specific runners or remotely fetching instructions at trading time. Test prompts and expected answers live under `service/tests/fixtures/`, outside installed and served runtime skills. The routing helper only prepares and grades explicit classifications; it does not launch a model or claim native-client activation.

The baseline metadata trial missed standalone quote/bar research: the agent reasonably found no matching description. `trust-risk` already contained an analysis reference, but its description emphasized entry sizing. The correction names market research, portfolio and fixed-income analysis and makes the read-only path explicit. Matching MCP startup instructions, UI metadata and README guidance now use that scope. General finance explanations, Trust Wallet, bank passwords and Rust implementation work stay outside these trading workflow skills.

The same development set improved from 11/12 to 12/12 classifications in fresh independent evaluators. A separate 12-case validation set also matched all expected choices, with no skill edits based on those validation answers. These are small, explicit selection trials with the inherited model, not statistical estimates or automatic client activation tests. All original answers and the baseline failure are retained in `.local/skills-research/`.

Three additional MCP scenarios cover account-choice ambiguity, short-position stop direction and unavailable market data. The research report exposed conflicting startup guidance and missing guidance for derived intervals/calendar assumptions; the final instructions address those narrowly. Product limitations such as generic market-data errors, ambiguous policy-layer labels and incomplete broker-state evidence remain recorded in the reports. A skill must expose those limits rather than claim to fix the broker or service by wording alone.
